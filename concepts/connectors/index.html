    Connectors¶

    A connector is a kind of access a cell needs: the login of its harness, a token for an API, the identity it clones, pushes and signs with, the credential a Realm pulls private images with. An identity is one stored Secret that fills a connector — a subscription token, a work GitHub token, a bot's SSH key.

    Connectors separate three decisions that used to be one:

    Decision Made by Where it lives
    Which connectors a cell requires the role and its harness components of the blueprint and the Config
    Which identity fills each one by default the operator, once Realm, Space or Stack spec.defaults
    Which identity one team or one cell uses the team (connectors) or --connector the Config's fill, or the cell's provenance

    So a token is stored once, picked by name, and replaced in one place.

    Trusted network only

    kuke serve — the web UI and its /api/connectors endpoints — has no authentication, and it can be bound to any address. Anyone who reaches it can create identities, change defaults and start cells that use them. Run it on a trusted network or loopback only. Secret material is write-only everywhere: no CLI verb, API response or error prints it.

    The connectors kuke ships¶

    Each connector is one file under team/connectors/<name>/connector.yaml.

    claude¶

    How a Claude Code cell authenticates. The three methods exclude each other; kuke team enables exactly one on every claude Config.

    Method Component Delivery Identity
    login claude-login the harness state volume none — log in once from an interactive cell
    subscription claude-subscription CLAUDE_CODE_OAUTH_TOKEN opaque Secret: a token from claude setup-token
    api-key claude-api-key ANTHROPIC_API_KEY opaque Secret: an Anthropic API key, billed per token

    login is the default: it is what a cell did before connectors existed. A subscription token is valid for a year and serves every role, so it is the method to choose when cells of several roles — or a headless task with an empty state volume — must start authenticated.

    codex¶

    How a Codex cell authenticates. Same shape: one method per codex Config.

    Method Component Delivery Identity
    login codex-login the harness state volume none — codex login from an interactive cell
    api-key codex-api-key OPENAI_API_KEY opaque Secret: an OpenAI API key
    access-token codex-access-token CODEX_ACCESS_TOKEN opaque Secret: a Codex access token (Business and Enterprise plans)

    github¶

    GitHub API access for the gh CLI: one method, token, delivered as GH_TOKEN through the github-token slot, with the gh image capability. The token is never a git credential — clone, push and signing use the git connector.

    git¶

    The identity a cell clones, pushes and signs with. A git identity is one ssh-key or basic-auth Secret that also carries readable facts:

    Field Type Meaning
    hosts (required) list Hosts or URL prefixes the Secret authenticates (github.com)
    author Name <email> Commit author
    committer Name <email> Committer; git falls back to the author
    sign commits, tags What to sign with the key (ssh-key only)
    allowedSignersRef secret reference Allowed-signers file used to verify (ssh-key only)

    git.identityRef names such a Secret — on a Realm, Space or Stack default, on a Config's git block, or on one repo's git. When a cell is rendered the daemon expands it into author, committer, one credential per host and, for an SSH key, signing with the same key. A field written next to the reference wins over the identity's, so a Config can keep the identity's key and credentials and state its own author. The rendered cell never carries the reference, only the result.

    A role with needs.repos requires the connector. It is optional for the cell to start: a public repository clones without an identity.

    registry¶

    The credential a Realm pulls private images with: a basic-auth Secret in the Realm, bound to a registry server by a spec.registryCredentials[] entry's secretRef. It is a Realm concern and never appears on a Config. See Private registry.

    Identities¶

    An identity is a Secret tagged with its connector:

    # A token identity
sudo kuke create secret work-github --connector github --from-file ./token

# A git identity: the key plus the readable facts
sudo kuke create secret bot-key --connector git --type ssh-key \
    --from-file ~/.ssh/id_ed25519 \
    --author 'Dev Bot <bot@example.com>' --hosts github.com --sign commits,tags

    --connector validates the Secret against the connector: its type must be one the connector accepts, required fields must be set, and each value must read as its declared type. Every field of the connector is a flag of its own (--author, --hosts, …) and can also be written --identity FIELD=VALUE.

    $ sudo kuke get secrets -o wide
NAME         TYPE     CONNECTOR  REALM    SPACE  STACK  CELL  IDENTITY
bot-key      ssh-key  git        default  -      -      -     author=Dev Bot <bot@example.com>; hosts=github.com; sign=commits,tags
work-github  opaque   github     default  -      -      -     -

    The tag and the fields are readable; the material never is. A Secret without a tag still works wherever it is named by hand — one created before connectors existed needs no migration — but a Secret tagged for one connector is refused for another.

    Defaults and precedence¶

    The identity of a connector is resolved when a cell is rendered, most specific first:

    1. the cell's own choice (--connector),
    2. the Config's fill,
    3. the Stack default,
    4. the Space default,
    5. the Realm default.

    A default is a spec.defaults.secrets entry keyed by the connector's slot (for git, spec.defaults.git.identityRef):

    apiVersion: v1beta1
kind: Realm
metadata:
  name: default
spec:
  namespace: default.kukeon.io
  defaults:
    secrets:
      github-token:
        secretRef: { name: work-github, realm: default }
    git:
      identityRef: { name: bot-key, realm: default }

    Defaults are live: a Config that chose no identity has no fill, so changing the default changes the identity of every such Config's next cell, with nothing to re-render. kuke team relies on this — it writes a Realm default for a slot only when no Realm, Space or Stack default exists yet, and never overwrites one.

    $ sudo kuke get configs -o wide
NAME                  ...  CONNECTORS
kuke-majordomo-claude ...  claude=login, github=work-github (realm)
team-dev-codex        ...  codex=login, git=bot-key (config), github=MISSING

    A required connector with no identity at any level is unresolved. Previewing or creating a cell from that Config fails with an error naming the connector; the web UI shows a Needs connector badge on the Config, counts the affected Configs on the Connectors page, and disables Create until a default is set or an identity is picked. A named identity that is missing, tagged for another connector or of the wrong type is an error even for an optional connector.

    Teams¶

    A team picks a method and an identity per connector in its kind: Team file or its TeamEntry; a role entry overrides the team for that role.

    apiVersion: kuketeams.io/v1
kind: Team
metadata:
  name: backend
spec:
  connectors:
    claude: { method: subscription, identity: claude-team }
    github: { identity: work-github }
    git: { identity: bot-key }
  roles:
    - name: reviewer
      source: agents
      path: roles/reviewer
      connectors:
        github: { identity: review-github } # this role only
    • method picks one of the connector's methods; empty selects its default.
    • identity names the Secret, name[@realm[/space[/stack]]]; without a scope it is looked up in the team's realm. Empty leaves the identity to the defaults.
    • A role entry that names no method keeps the team's method, and the team's identity unless it names its own. One that names a method states the whole choice.
    • A role entry also gives the role's cells a connector the role does not ask for itself.

    Every rendered Config lists all its connector components under spec.components — the harness's auth method, git when the role works on repositories, and each connector the role or the team asks for. Only an identity the team chose is written as a fill on the Config; everything else stays with the defaults. A team's git identity is written on the Config (spec.git.identityRef), never on the Stack, because other teams share the Stack.

    Roles written before connectors existed keep rendering: a role that lists the old secret names (claude-code-oauth-token, anthropic-api-key, openai-api-key, gh-token) selects the method that delivers that secret. Two such names of one connector are alternatives — the first method wins and kuke team says so; set connectors.<name>.method to choose.

    Per-cell overrides¶

    sudo kuke create cell --from-config team-dev-claude --connector github=other-github
sudo kuke run -c team-dev-claude --connector git=release-key@ops
sudo kuke create cell --from-config team-dev-codex --connector-method codex=api-key --connector codex=my-openai-key

    --connector <connector>=<secret>[@realm[/space[/stack]]] uses another identity for this one cell. The override is recorded in the cell's provenance (spec.provenance.connectorOverrides), so kuke restart and a reconcile-driven recreate render the cell with the same identity, and kuke create cell --clone carries it over. The flag is valid with --from-config only. An unknown connector, a missing Secret, or a Secret tagged for another connector is rejected before anything is created.

    --connector-method <connector>=<method> uses another method of a connector for this one cell — for example a codex Config on login started once with api-key. The blueprint already carries every method of the connector as one exclusive group, so the cell enables the picked method's component in place of the one the Config enables; the Config itself is not changed. The new method's identity resolves as usual: a --connector override, the Config's fill, then the Stack, Space and Realm defaults — a Config's fill for its own method's slot does not carry over. The choice is recorded in spec.provenance.connectorMethods and kept by kuke restart, a reconcile-driven recreate and --clone. A connector the blueprint declares no methods for, a method it does not declare, or a connector the Config does not require (a method pick swaps a method, it never adds a connector) is rejected. Valid with --from-config only.

    In the web UI's New Cell flow every required connector is pre-selected with its effective method and identity. A connector with several methods offers a method picker; choosing another identity or method sends the same overrides, and the preview shows the methods and identities the cell will use. A per-cell pick is allowed on a team-owned Config too: only the Config's own page shows its identities read-only, because kuke team add re-renders it.

    Why login volumes are not shared across roles¶

    The login methods keep the session in the harness state volume, and that volume is per role — kuke-majordomo-claude and team-dev-claude each log in once. Sharing one volume across roles is deliberately not supported:

    • The state directory also holds the role itself — settings, skills and instructions the role's launch installs there — so a shared volume would let one role's content overwrite another's.
    • A Codex login's refresh token is single-use. Two cells refreshing one copied login invalidate each other.

    When several roles must start authenticated without an interactive login each, use a token method instead: a Realm-default claude-subscription identity authenticates every claude cell, interactive or headless, with an empty state volume.

    Adding a connector¶

    A connector is data. Adding one is one file, team/connectors/<name>/connector.yaml; no Go and no TypeScript names a connector, and a test (pkg/team/connector/guard_test.go) enforces it.

    apiVersion: kuketeams.io/v1
kind: Connector
metadata:
  name: example-token # must match the directory
spec:
  title: Example
  description: An API token for the example service.
  scopes: [realm, space, stack]
  identity:
    secretTypes: [opaque]
    fields:
      - name: account
        required: true
        help: Account the token belongs to.
  methods:
    - name: token
      default: true
      delivery: env
      description: A token delivered as EXAMPLE_TOKEN.
      requires: [example-cli]
      secret:
        name: example-token
        envName: EXAMPLE_TOKEN

    With that file the connector appears in kuke create secret --connector, team connectors, kuke create cell --connector, and the web UI's Connectors page and pickers.

    Field Meaning
    title, description Display name and what the access is for
    identity.secretTypes Secret types accepted: opaque, basic-auth, ssh-key
    identity.fields[] Readable identity fields: name, type (string, list, person, secret), required, enum, secretTypes, help
    scopes Where a default may be set: realm, space, stack (empty allows all)
    harness The harness this connector authenticates; kuke team enables exactly one method on each of its Configs
    group Exclusion group of the method components (defaults to the connector's name)
    optional A cell may start without an identity
    methods[] The ways to deliver the connector; exactly one is default: true
    methods[].component Blueprint component name; <connector>-<method> when empty
    methods[].delivery env, file or stateVolume
    methods[].requires Image capabilities the method needs
    methods[].secret The slot: name, and envName (env) or an absolute mountPath (file); secretName and aliases for older roles
    delivery (no methods) git or registry: a connector delivered by a handler

    Component names and slot names are unique across the catalog.

    Delivery handlers¶

    The delivery says how an identity reaches a cell:

    Delivery What it does
    env The Secret's value is set as the environment variable of the method's slot
    file The Secret's value is mounted read-only at the slot's path
    stateVolume Nothing is delivered: the login lives in the harness state volume
    git git.identityRef is expanded into author, committer, credentials and signing
    registry The Secret is the pull credential of a Realm's registryCredentials[] entry

    env, file and stateVolume need no code. git and registry are the two handlers implemented in the daemon (internal/connector/handlers.go names their fields); a new connector with one of the first three deliveries is only a file.

    The daemon keeps no catalog. kuke team copies each connector's definition into the blueprint component that requires it, so the daemon validates and resolves identities from the blueprint alone — including for a connector added after the daemon was built.
